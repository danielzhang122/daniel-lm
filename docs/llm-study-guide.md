Training itself is a loop that repeats thousands of times:

```
   ┌─────────────────────────────────────────────────────────────┐
   │ 1. grab some text                                           │
   │ 2. FORWARD: model guesses the next token at every position  │
   │ 3. LOSS: grade the guesses (one number, lower = better)     │
   │ 4. BACKWARD (backprop): work out how each knob caused error │
   │ 5. UPDATE: nudge every knob a tiny bit to reduce the error  │
   └──────────────────────────── repeat ─────────────────────────┘
```

# PART 1: The Big Idea

## Chapter 1: What is a language model?

> 🧒 **ELI5:** A language model is a program that reads some words and guesses what word comes next. That's all it does. To write a sentence, it guesses one word, adds it to the end, and then guesses the next one, again and again.

A **language model (LM)** is a program that has learned to answer one question:

> **Given the text so far, what piece of text comes next?**

```
"The cat sat on the ___"
      mat    ████████████████  41%
      floor  ████████          19%
      couch  ████               9%
      bed    ███                7%
      ...    (16,380 more options, each tiny)
```

Notice it doesn't give *one* answer. It gives a **probability** (a percentage) for every possible next piece. All the probabilities add up to 100%.

### 1.1 How guessing one word becomes writing an essay

Guess a word, stick it on the end, guess again:

```
"The cat"             → guess "sat"
"The cat sat"         → guess "on"
"The cat sat on"      → guess "the"
"The cat sat on the"  → guess "mat"
...
```

This is called **autoregressive generation**: *auto* (self) + *regressive* (feeding back). The model feeds its own output back in as input. ChatGPT, Claude and your model all work this way. A chatbot is a next-word guesser that has been trained on conversations, so that the "next words" after a question happen to be an answer.

### 1.2 Why such a simple game makes something smart

> 🧒 **ELI5:** Guessing the next word correctly is hard. To get good at it, the model has to learn spelling, grammar, facts, and how ideas connect. Nobody teaches it those things directly. It picks them up because they help it guess better.

To guess the next word *really* well, you have to understand a lot:
- `"The capital of France is ___"` → you need **facts**.
- `"She dropped the glass and it ___"` → you need **common sense** (glass breaks).
- `"If x = 3, then 2x = ___"` → you need **reasoning**.
- `"The keys to the cabinet ___"` → you need **grammar** ("are", not "is", because *keys* is plural).

Nobody programs any of this in. The model is pushed, billions of times, to make better guesses, and the cheapest way to make better guesses turns out to be learning these patterns.

### 1.3 "GPT"

Your model is a **GPT**: **G**enerative **P**re-trained **T**ransformer.
- **Generative**: it generates text.
- **Pre-trained**: it's first trained on a big pile of general text (Wikipedia), before any special training such as conversation.
- **Transformer**: the architecture, meaning how the model is wired inside. Chapters 6–12 cover it.

> 💡 **Key idea:** A language model is a next-token guessing machine. Everything else (chatting, answering, writing) is that one skill used in a loop.

> **Q: Why does a language model output a probability for *every* possible next word instead of just one word?**
>
> A: Because many continuations are often reasonable, and because training needs a smooth score to improve. Grading "how much probability went to the right answer" gives partial credit, so the model can get *gradually* better. Probabilities also let generation sample varied text.

## Chapter 2: The math toolkit (only what you need)

> 🧒 **ELI5:** A vector is a list of numbers. A matrix is a grid of numbers. Multiplying a list by a grid gives you a new list. A derivative tells you: if this number goes up a little, does that other number go up or down, and by how much? That's all the math you need.

You need five ideas. Each one is small.

### 2.1 Vectors: a list of numbers

A **vector** is a list of numbers, like `[0.2, -1.5, 3.0]`. Its **size** (or **dimension**) is how many numbers it has. That one has size 3.

In your model, every token is represented as a vector of **512 numbers**. That size is the model's **width** (`width` in `model.py`); the bigger `big` run uses a width of 768. You can think of it as a "personality profile" for that token, where each number measures some trait. Nobody chooses the traits; the model learns them.

### 2.2 Matrices and matrix multiplication

A **matrix** is a grid of numbers with rows and columns. A **3×2** matrix has 3 rows and 2 columns:

```
W = [[1, 0],
     [0, 1],
     [1, 1]]
```

**Matrix multiplication** is how a model *mixes* numbers. Here's the version you'll see everywhere: take an input vector `x` and produce an output vector `y`, where **each output number is a weighted sum of all the inputs**.

Worked example with `x = [1, 2]` and the `W` above. Each **row** of W gives the weights for one output:

```
y[0] = 1·1 + 0·2 = 1     (row 0 = [1, 0])
y[1] = 0·1 + 1·2 = 2     (row 1 = [0, 1])
y[2] = 1·1 + 1·2 = 3     (row 2 = [1, 1])

y = [1, 2, 3]
```

So W turned a size-2 vector into a size-3 vector. In PyTorch this is written `y = x @ W.T`. The `@` means "matrix multiply" and `.T` means **transpose** (flip rows and columns). PyTorch stores W as (outputs × inputs), so we flip it.

**The shape rule:** `(A × B) @ (B × C) → (A × C)`. The inner numbers must match, and they "cancel". If your shapes don't line up, the code crashes. That's actually helpful, because it catches bugs.

> 🧪 **Try it 2.1:** With the same `W`, compute `y` for `x = [3, -1]`.

### 2.3 Tensors and shapes

> 🧒 **ELI5:** A tensor is just numbers stored in a box with some number of sides: a single number, a list, a table, or a stack of tables. The **shape** is a short list saying how long each side is. A shape of `(3, 4)` means a table with 3 rows and 4 columns, so 12 numbers. Multiply the shape's numbers together and you get how many numbers are inside.

**First, forget "direction."** In physics, a scalar is a size with no direction (like temperature) and a vector has a direction (like velocity). Machine learning borrows the same words but uses them more simply. Here, they only describe **how the numbers are arranged**:

- A **scalar** is one number by itself.
- A **vector** is a list of numbers.
- A **matrix** is a table of numbers (rows and columns).
- A **tensor** is the general word for any of these, including stacks of tables with even more layers.

A token's 512-number vector isn't an arrow pointing somewhere. It's just 512 numbers in a row, each one describing something about the token.

#### What the shape tells you

The best way to understand a shape: **how many position numbers do you need to point at one single value?**

| Name | Dimensions | To find one number you need... | Example | Shape |
|---|---|---|---|---|
| scalar | 0 | nothing, there's only one number | `7` | `()` |
| vector | 1 | 1 position: which item in the list | `[4, 9, 2]` | `(3,)` |
| matrix | 2 | 2 positions: which row, which column | 2 rows of 3 numbers | `(2, 3)` |
| 3-D tensor | 3 | 3 positions: which table, which row, which column | 4 tables, each 2 × 3 | `(4, 2, 3)` |

So:
- **The number of entries in the shape** is the number of dimensions. `(4, 2, 3)` has 3 entries, so it's 3-D.
- **Each entry** is how many options there are for that position. `(4, 2, 3)` means 4 tables, each with 2 rows, each row with 3 numbers.
- **Multiply the entries** to get the total count of numbers: `4 × 2 × 3 = 24`.

A scalar's shape is empty, `()`, because you don't need any position to find its one number.

#### Building up, one dimension at a time

Each new dimension means "many of the previous thing":

```
scalar        7                                   shape ()          1 number

vector        [4, 9, 2]                           shape (3,)        3 numbers

matrix        [[4, 9, 2],                         shape (2, 3)      6 numbers
               [1, 0, 5]]                         2 rows, 3 columns

3-D tensor    [ [[4, 9, 2], [1, 0, 5]],           shape (4, 2, 3)   24 numbers
                [[...],     [...]   ],            4 matrices,
                [[...],     [...]   ],            each 2 × 3
                [[...],     [...]   ] ]
```

To read one value, you give one position per dimension, counting from 0. In the matrix above, `[1, 2]` means row 1, column 2, which is `5`.

#### The shapes in this project

| Dimensions | Example shape | What it holds | How to read the shape |
|---|---|---|---|
| 0 | `()` | the loss, like `3.21` | one number |
| 1 | `(512,)` | one token's vector | 512 numbers |
| 2 | `(16384, 512)` | the whole token table | 16,384 tokens, 512 numbers each |
| 3 | `(2, 512, 512)` | a batch of text going through the model | 2 chunks of text, 512 tokens each, 512 numbers per token |
| 4 | `(2, 8, 512, 512)` | attention scores | 2 chunks, 8 heads, and for each of 512 tokens, a score for each of 512 tokens |

Check the token table: `16,384 × 512 = 8,388,608` numbers. That's one shape, and you already know how big it is.

**Shape letters used in this guide (and in `model.py`):**

| Letter | Meaning | Value in this project |
|---|---|---|
| `b` | **batch**: how many text chunks processed at once | 2 |
| `t` | **time**: how many tokens per chunk (position in the sentence) | up to 512 |
| `c` | **channels**: the vector width per token | 512 |
| `h` | **heads**: parallel attention units | 8 |
| `d` | per-head width = `c / h` | 64 |
| `V` | **vocabulary** size: how many different tokens exist | 16,384 |

So the main data flowing through the model has shape **`(b, t, c)`**. Read it left to right: "for each chunk of text, for each token in it, 512 numbers." Pointing at one value takes three positions, like `[1, 40, 7]`: chunk 1, token 40, number 7 of that token's vector.

When you're confused, **write the shapes down.** Half of deep learning debugging is checking that shapes line up.

### 2.4 `exp` and `log`

- `exp(x)` = e^x, where e ≈ 2.718. It turns *any* number into a *positive* number. Big inputs become huge, negative inputs become tiny but still above zero. `exp(0)=1`, `exp(2)≈7.39`, `exp(-2)≈0.135`.
- `log(x)` (natural log) is the reverse of exp. `log(1)=0`, `log(0.5)≈-0.69`, `log(0.01)≈-4.6`. The log of a number between 0 and 1 is **negative**, and gets more negative as the number gets smaller.

We use `exp` to turn scores into probabilities (Chapter 13) and `log` to grade them.

### 2.5 Derivatives: "how sensitive is the output to this input?"

The **derivative** of `y` with respect to `x`, written `dy/dx`, answers:

> If I nudge `x` up by a tiny bit, how much does `y` change, and in which direction?

Examples:
- `y = 3x` → `dy/dx = 3`. Nudge x by 0.01 and y goes up by 0.03.
- `y = x²` → `dy/dx = 2x`. At x=5 the slope is 10. At x=−5 it's −10, so nudging x *up* makes y go *down*.
- `y = -x` → `dy/dx = -1`.

You can always **measure** a derivative by nudging:
```
dy/dx ≈ ( y(x + 0.0001) − y(x − 0.0001) ) / 0.0002
```
This is called a **finite difference**. Remember it, because in Chapter 16 we'll use it to check our code.

#### The derivative is the slope

Draw `y = x²` as a curve. The derivative at a point is the **slope** of the curve right there: how steep it is, measured as **rise over run** (how far up you go for each step to the right).

A curve has no single slope, because its steepness changes as you move along it. The trick is to **zoom in**. Look at `y = x²` near `x = 3`:

| x | y = x² | rise (change in y) | run (change in x) | rise ÷ run |
|---|---|---|---|---|
| 3 → 4 | 9 → 16 | 7 | 1 | 7 |
| 3 → 3.1 | 9 → 9.61 | 0.61 | 0.1 | 6.1 |
| 3 → 3.01 | 9 → 9.0601 | 0.0601 | 0.01 | 6.01 |
| 3 → 3.001 | 9 → 9.006001 | 0.006001 | 0.001 | 6.001 |

The smaller the step, the closer rise ÷ run gets to **6**, and the formula `dy/dx = 2x` gives `2 × 3 = 6`. Zoomed in far enough, any smooth curve looks like a straight line, and the derivative is that line's slope. (The line is called the **tangent line**: the straight line that just touches the curve at that point.)

What the sign and size of the slope tell you:

| Slope | The curve here is... | Nudging x up makes y... |
|---|---|---|
| big positive (e.g. +6) | climbing steeply | go up a lot |
| small positive (e.g. +0.1) | climbing gently | go up a little |
| 0 | flat (the bottom of a valley or the top of a hill) | barely change |
| negative (e.g. −10) | going downhill | go down |

That last row is the whole basis of training: if you know which way is downhill, you know which way to move.

#### Gradients: slopes in more than one direction

A **gradient** is a collection of derivatives, one per input. Each one is a **partial derivative**: the slope when you nudge *that one input* and hold all the others still.

**A 3D example.** Take a function with two inputs:
```
f(x, y) = x² + y²
```
Picture it as a landscape: `x` and `y` are your position on the ground (east–west and north–south), and `f` is the height. This one is a smooth **bowl** with its lowest point, height 0, at `(0, 0)`. Here are some heights:

| | x = 0 | x = 1 | x = 2 | x = 3 |
|---|---|---|---|---|
| **y = 2** | 4 | 5 | 8 | 13 |
| **y = 1** | 1 | 2 | 5 | **10** ← you are here |
| **y = 0** | 0 (bottom) | 1 | 4 | 9 |

Stand at `(3, 1)`, height 10. There's one slope per direction:
- **East–west** (nudge x, hold y still): `∂f/∂x = 2x = 6`.
- **North–south** (nudge y, hold x still): `∂f/∂y = 2y = 2`.

(The curly `∂` just means "partial derivative": the slope along one input while the others stay fixed.)

So the gradient at `(3, 1)` is the arrow **`[6, 2]`**. It's written `∇f`, read "grad f".

#### The gradient points up the steepest slope

The gradient isn't just a list of numbers: it's an **arrow on the ground**, and it points in the direction where the landscape **climbs fastest**. Its length is how steep that climb is.

You can check this at `(3, 1)`. Take a small step of length 0.01 in different directions and see how much the height changes:

| Direction you step | Height change (about) |
|---|---|
| Along the gradient `[6, 2]` | **+0.063** (the steepest climb possible) |
| East only `[1, 0]` | +0.060 |
| Diagonal `[1, 1]` | +0.057 |
| North only `[0, 1]` | +0.020 |
| Sideways, at a right angle to the gradient | 0 (walking along the bowl's side, staying level) |
| **Against** the gradient `[−6, −2]` | **−0.063** (the steepest drop possible) |

No direction climbs faster than the gradient, and none drops faster than its exact opposite. Why: the height change in any direction is the gradient's dot product with that direction, which is largest when the two point the same way. The climb along the gradient is its length, `√(6² + 2²) ≈ 6.32`, times the step size.

So **the negative gradient points down the steepest slope**. Following it is called **steepest descent**, or **gradient descent**, and it's exactly how the model learns:

```
new position = position − learning_rate × gradient
```

One step from `(3, 1)` with learning rate 0.1:
```
(3, 1) − 0.1 × [6, 2] = (2.4, 0.8)
height: 10  →  2.4² + 0.8² = 5.76 + 0.64 = 6.4      (downhill!)
```
**Important: recompute the gradient at every new position.** The gradient `[6, 2]` was the slope at `(3, 1)` only. The ground has a different tilt at `(2.4, 0.8)`, so the next step uses the gradient *there*: `[2 × 2.4, 2 × 0.8] = [4.8, 1.6]`. Reusing `[6, 2]` would be walking on an old map: it would keep pushing in the same direction at the same strength, and could carry you straight past the bottom of the bowl.

So each step is: **measure the slope where you're standing, step, measure again.**

| Step | Position (x, y) | Gradient here `[2x, 2y]` | Height `x² + y²` |
|---|---|---|---|
| 0 | (3, 1) | [6, 2] | 10 |
| 1 | (2.4, 0.8) | [4.8, 1.6] | 6.4 |
| 2 | (1.92, 0.64) | [3.84, 1.28] | 4.096 |
| 3 | (1.536, 0.512) | [3.072, 1.024] | 2.621 |
| 4 | (1.229, 0.410) | [2.458, 0.819] | 1.678 |
| 5 | (0.983, 0.328) | [1.966, 0.655] | 1.074 |

Each row's position is the row above minus 0.1 × the row above's gradient. Two things to notice:
- **The gradient shrinks as you approach the bottom**, because the bowl flattens out. So the steps get smaller on their own, even though the learning rate stays at 0.1.
- At the very bottom, `(0, 0)`, the gradient is `[0, 0]`: flat ground, nowhere downhill to go, so the steps stop.

Repeat this and you slide toward the bottom of the bowl at `(0, 0)`. In training, this is why the model has to run a fresh forward and backward pass every step: changing the knobs changes the landscape's slope under them, so last step's gradient is already out of date.

Notice that the step moved `x` (the steep direction) more than `y` (the gentle one). Each input moves in proportion to its own slope.

#### From 2 knobs to 34 million

The bowl has 2 inputs, so you can picture it in 3D. Your model has about 34 million knobs, so its loss landscape has 34 million "ground" directions plus one for height. Nobody can picture that, but the math is identical: the gradient is an arrow with 34 million numbers, each one saying "this knob: push this way, this hard", and the negative gradient is still the steepest way down. Chapter 3 walks down this landscape, and Chapter 14 shows how to compute those 34 million numbers efficiently.

> 💡 **Key idea:** A derivative is the slope of a curve: "nudge this, and that changes by this much." A gradient collects one slope per input and points up the steepest hill, so stepping *against* it is the steepest way down. Training is entirely about computing these slopes for every knob and stepping downhill.

> **Q: A matrix of shape `(4, 3)` multiplies (`@`) a matrix of shape `(3, 7)`. What shape comes out?**
>
> A: `(4, 7)`. The inner 3s cancel.
>
> **Q: If `y = x²` and `x = 3`, is the derivative positive or negative? What does that mean in words?**
>
> A: `dy/dx = 2x = 6`, positive. Nudging x up makes y go up, about 6× as much.

## Chapter 3: How machines learn

> 🧒 **ELI5:** The model is full of numbers that can be changed. At first they're random, so its guesses are bad. We measure how bad a guess was. Then we change each number a tiny bit so the next guess is a little less bad. We repeat this many thousands of times, and the guesses get good.

### 3.1 Knobs

A model is a math function with **adjustable numbers inside**. These are called **parameters** or **weights**, but think of them as **knobs**.

Tiny example: a "model" with one knob, `w`:
```
guess = w × x
```
If `w = 3` and `x = 2`, the guess is 6. Change the knob and the guess changes. Your real model is the same idea with **about 34 million knobs**.

### 3.2 Loss: grading the guess

The **loss** is a single number that measures how bad the guess was. **Lower is better. Zero is perfect.**

A simple loss, "squared error":
```
loss = (guess − correct_answer)²
```
If the guess is 6 and the answer is 10: `loss = (6 − 10)² = 16`.

(Your language model uses a different loss called *cross-entropy*, covered in Chapter 13, but the idea is the same.)

### 3.3 Gradient descent: walking downhill

> 🧒 **ELI5:** For each number in the model, we work out: should it go up or down to make the error smaller? Then we move it a small step in that direction. The learning rate is how big that step is. Too small and learning is slow. Too big and the numbers overshoot and the error gets worse.

Picture the loss as a **landscape**. Every possible knob setting is a location, and the loss is the height. Training = **getting to the lowest valley**.

You're blindfolded. You can't see the valley, but you *can* feel the slope under your feet. That slope is the **gradient**. So:

1. Feel the slope (compute the gradient).
2. Take a small step downhill.
3. Repeat.

As an update rule:
```
knob = knob − learning_rate × gradient
```
The **minus** sign is what makes you go *down*hill. The **learning rate (LR)** is your step size.

### 3.4 Worked example: one knob, full loop

Task: learn `w` so that `w × 2 = 10`. (The right answer is obviously w = 5, but the computer doesn't know that.)

Start: `w = 3`, `x = 2`, `answer = 10`, `learning_rate = 0.05`.

| Step | w | guess = w·2 | loss = (guess−10)² | gradient dL/dw = 2·(guess−10)·x | new w = w − 0.05·grad |
|---|---|---|---|---|---|
| 1 | 3.000 | 6.000 | 16.00 | 2·(−4)·2 = **−16** | 3 + 0.8 = 3.800 |
| 2 | 3.800 | 7.600 | 5.76 | 2·(−2.4)·2 = −9.6 | 3.800 + 0.48 = 4.280 |
| 3 | 4.280 | 8.560 | 2.07 | −5.76 | 4.568 |
| 4 | 4.568 | 9.136 | 0.75 | −3.46 | 4.741 |
| … | → 5 | → 10 | → 0 | → 0 | |

Notice:
- A **negative** gradient means "increasing w lowers the loss", so the update increases w.
- As we get closer, the gradient shrinks and the steps get smaller on their own.
- Where did `dL/dw = 2·(guess−10)·x` come from? From the **chain rule**, the core of backprop. Chapter 14 covers it.

### 3.5 Choosing the learning rate

```
LR too small:  ·→·→·→·→·→·→·→·→·→·→·  (takes forever)
LR just right: ·———→·——→·→·          (gets there)
LR too big:    ·————————————→·  ←————————————·  (overshoots, bounces, can explode)
```
Your project uses a *changing* learning rate (Chapter 17.6).

> 💡 **Key idea:** Learning = repeatedly (1) measuring how wrong you are, (2) computing which way each knob should turn, (3) turning each knob a little. Steps 1–2 are "forward + backward", step 3 is "the optimizer".

> 🧪 **Try it 3.1:** Redo the table above with `learning_rate = 0.3`. What happens? (Hint: watch the sign of `guess − 10`.)

> **Q: If a knob's gradient is `+2.0`, should the knob go up or down to reduce the loss?**
>
> A: Down. A positive gradient means increasing the knob increases the loss, so move the opposite way.

# PART 2: Text → Numbers

## Chapter 4: Tokenization

> 🧒 **ELI5:** Computers can only work with numbers, not words. So we split text into small pieces called tokens, and each token gets an ID number. A common word is usually one token. A rare word is split into a few smaller tokens.

### 4.1 Why we need it

The model only does math on numbers, so text must become numbers. The tool that does this is a **tokenizer**. It chops text into pieces called **tokens**, and each token has an **ID** (an integer).

```
"The cat sat"  →  ["The", " cat", " sat"]  →  [464, 3797, 3332]     (IDs are illustrative)
```

### 4.2 Three ways to chop

| Method | Example for "unhappiness" | Vocabulary size | Problem |
|---|---|---|---|
| Characters | `u n h a p p i n e s s` (11 tokens) | tiny (~100) | sequences get very long; the 512-token window holds little text |
| Whole words | `unhappiness` (1 token) | enormous (millions) | any word not in the list is unknown; "skibidi" breaks it |
| **Subwords** ✔ | `un happiness` (2 tokens) | you choose (16,384 here) | none of the above. Common words are 1 token, rare words are a few pieces |

Your project uses subwords, built with an algorithm called **BPE**.

### 4.3 BPE (Byte Pair Encoding): the algorithm

> 🧒 **ELI5:** Start with every letter as its own piece. Find the two pieces that appear next to each other most often in the text, and join them into one new piece. Repeat this thousands of times. The pieces you end up with are the tokens.

**Idea:** start with single characters. Repeatedly find the **pair of neighbors that appears most often** and **glue it into a new token**. Stop when you have as many tokens as you want.

#### Worked example

Pretend our whole dataset is these words, with how many times each appears:

| word | count |
|---|---|
| cat | 8 |
| cats | 3 |
| hat | 6 |
| chat | 2 |
| that | 5 |

**Start:** every word is split into letters. Vocabulary = `{a, c, h, s, t}`.

**Round 1:** count every neighboring pair, weighted by how often the word appears:

| pair | where it appears | total |
|---|---|---|
| a t | cat(8) + cats(3) + hat(6) + chat(2) + that(5) | **24** ← winner |
| h a | hat(6) + chat(2) + that(5) | 13 |
| c a | cat(8) + cats(3) | 11 |
| t h | that(5) | 5 |
| t s | cats(3) | 3 |
| c h | chat(2) | 2 |

→ **Merge rule #1: `a + t → at`.** Now the words are: `c·at`, `c·at·s`, `h·at`, `c·h·at`, `t·h·at`.

**Round 2:** recount. `h + at` appears 6+2+5 = **13** (the most).
→ **Merge rule #2: `h + at → hat`.** Words: `c·at`, `c·at·s`, `hat`, `c·hat`, `t·hat`.

**Round 3:** `c + at` = 8+3 = **11**.
→ **Merge rule #3: `c + at → cat`.** Words: `cat`, `cat·s`, `hat`, `c·hat`, `t·hat`.

**Round 4:** `t + hat` = **5**.
→ **Merge rule #4: `t + hat → that`.** Words: `cat`, `cat·s`, `hat`, `c·hat`, `that`.

After 4 merges, the vocabulary is `{a, c, h, s, t, at, hat, cat, that}`. Common words became single tokens, while `cats` = `cat + s` and `chat` = `c + hat`, built from pieces. **That's BPE.** Your real tokenizer did this **16,126 times** on Wikipedia.

The output of training is two things:
1. **The vocabulary**: every token and its ID.
2. **The merge rules, in order.** Order matters.

#### How the IDs are numbered

A token's ID is its **place in the vocabulary list**, *not* its position in your sentence. The starting characters get the first numbers, and each merge gets the next free number in the order it was learned. In the toy example:

| Token | a | c | h | s | t | at | hat | cat | that |
|---|---|---|---|---|---|---|---|---|---|
| ID | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |

Your real tokenizer works the same way:

| IDs | What they are |
|---|---|
| 0, 1 | The special tokens `<unk>` and `<eos>` (Section 4.6) |
| 2–257 | The 256 starting bytes (Section 4.4) |
| 258 | The first merge learned: `Ġt` (a space + "t"; `Ġ` is how the tokenizer writes a space) |
| 259 | The second merge: `he` |
| … | one new ID per merge |
| 16,383 | The last merge: `national` |

Because the ID belongs to the token and not to the slot, **the same token always gets the same ID**, wherever it appears:

```
"the cat sat on the cat"
 the   Ġcat  Ġsat  Ġon  Ġthe  Ġcat
 1220  6097  4788  328  264   6097
```

` cat` is 6097 both times. `the` (1220) and ` the` (264) differ because one has a leading space. So where does the model learn *where* each token sits? From a separate table, the **position embedding** (Section 7.2), which is added to the token's own vector.

#### Encoding new text

To tokenize a new word, split it into characters and then **apply merge rules in the order they were learned** until none apply:
```
"cats"  → c a t s
rule 1 (a+t):   c at s
rule 2 (h+at):  (no h, skip)
rule 3 (c+at):  cat s
rule 4 (t+hat): (skip)
→ ["cat", "s"]
```

> 🧪 **Try it 4.1:** Using the 4 merge rules above, tokenize `"thats"` and `"scat"`.

### 4.4 Byte-level: never get stuck

Your tokenizer doesn't start from letters. It starts from **bytes**.

All text on a computer is stored as **bytes** (numbers 0–255) using a standard called **UTF-8** (Unicode Transformation Format, 8-bit). Plain English letters are 1 byte each. `é` is 2 bytes. An emoji is 4 bytes.

Starting from all 256 bytes means **any text can be tokenized**: any language, emoji, typos, code. In the worst case it falls back to raw bytes. That's why the `<unk>` ("unknown") token practically never gets used.

**The `Ġ` mystery:** if you open `tokenizer.json`, you'll see tokens like `Ġthe`. Some bytes (space, newline, control codes) are invisible or confusing, so byte-level BPE swaps each one for a visible stand-in character. **`Ġ` means a space**, and `Ċ` means a newline. So `Ġthe` is really `" the"`.

### 4.5 Pre-splitting with a pattern

Before BPE runs, the text is cut into word-like chunks with a pattern (a "regex", short for regular expression), the same one GPT-2 used:

```
"Hello world's 42!"  →  "Hello" | " world" | "'s" | " 42" | "!"
```

Two important consequences:
1. **The space stays attached to the front of the word.** So `" the"` (mid-sentence) and `"the"` (start of text) are *different* tokens.
2. **Merges never cross these chunk borders.** You'll never get a token like `"o w"`.

### 4.6 Special tokens

| Token | Meaning | Used for |
|---|---|---|
| `<eos>` | **E**nd **O**f **S**equence | Added after every article and every assistant reply. The model learns that `<eos>` means "I'm done", and generation stops when it produces one. |
| `<unk>` | **Unk**nown | Required by the library; basically never used with bytes. |

### 4.7 This project's tokenizer

> 📁 **In the code:** `prepare.py`, lines 51–58
> ```python
> tok = Tokenizer(models.BPE(unk_token='<unk>'))
> tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
> tok.decoder = decoders.ByteLevel()
> trainer = trainers.BpeTrainer(vocab_size=16384, special_tokens=['<unk>', '<eos>'],
>                               initial_alphabet=pre_tokenizers.ByteLevel.alphabet())
> tok.train_from_iterator(... 10,000 training articles ..., trainer)
> ```

- **Library:** `tokenizers` from **Hugging Face (HF)**, a company that makes open-source AI tools. Only the *tool* came from HF. The vocabulary was learned from **your** data.
- **Vocabulary:** 16,384 = 256 bytes + 2 special tokens + 16,126 merges.
- **Why 16,384?** It fits in a **uint16** (unsigned 16-bit integer, values 0–65,535), so each token takes only 2 bytes on disk.
- The tokenizer is saved as `tokenizer.json`, and its **fingerprint** (a SHA-256 hash, explained in Chapter 5) is recorded. The model refuses to run with a different tokenizer, because token #5000 would mean something totally different.

> 💡 **Key idea:** A tokenizer is a learned dictionary of text pieces. BPE builds it by repeatedly gluing the most common pair. The model never sees letters, only token IDs.

> **Q: Why is `" cat"` a different token from `"cat"`?**
>
> A: Because the pre-splitting pattern keeps the space attached to the word, and BPE learned `" cat"` (mid-sentence) and `"cat"` (start of text or after a symbol) as separate pieces.
>
> **Q: Why can a byte-level tokenizer never fail to encode text?**
>
> A: Every possible piece of text is made of bytes, and all 256 bytes are in the base vocabulary. Worst case, each byte becomes its own token.

## Chapter 5: The data pipeline

> 🧒 **ELI5:** We download Wikipedia. We delete the parts that aren't useful, like reference lists. We turn all the text into token IDs and save them. We keep about 1 in 100 articles aside and never train on them, so we can test the model on text it hasn't seen.

> 📁 **In the code:** `prepare.py`, `cleaning.py`

1. **Download** English Wikipedia (via HF's `datasets` library), *streamed* piece by piece so it never has to fit on disk all at once, and **shuffled**.
2. **Clean** each article (`cleaning.py`): cut everything from junk sections like "References", "External links" and "See also" to the end, drop "Category:" lines, squash extra blank lines. Skip articles under 200 characters.
3. **Split into train and validation.**
   - **Training set:** what the model learns from.
   - **Validation set ("val"):** about 1% of articles the model **never trains on**. It's a pop quiz to check that the model learned general patterns instead of memorizing.
   - How it decides: each article's ID goes through **SHA-256** (Secure Hash Algorithm, 256-bit), which turns any input into a random-looking but **always identical** number. If that number mod 100 is 0, the article goes to val. Same article → same side, every time, on every computer.
4. **Train the tokenizer** on 10,000 *training* articles only, so the val set doesn't leak in.
5. **Encode** every article: `title + "\n\n" + text` → token IDs → add `<eos>`.
6. **Pack** all the IDs end-to-end into one giant file: `train.bin` and `val.bin`. Each ID is 2 bytes (uint16). No padding, no gaps. Articles are separated only by `<eos>`.
7. **Write `metadata.json`**: token counts, the Wikipedia version, and the tokenizer fingerprint.

```
train.bin:  [464, 3797, 3332, ..., 1(<eos>), 818, 2231, ..., 1(<eos>), ...]
            └────── article 1 ──────┘        └────── article 2 ──────┘
```

> **Q: Why must the validation articles never be used for training?**
>
> A: Val measures how well the model handles text it hasn't seen. If it trained on val, a low val loss could just mean memorization, and you'd lose your honest check.

## Chapter 7: Embeddings, turning IDs into vectors

> 🧒 **ELI5:** The model has a table with one row per token. Each row is a list of 512 numbers. To read a token, the model looks up its row. It also adds numbers from a second table that say where the token is in the sentence (1st, 2nd, 3rd...), because word order matters.

An ID like `3797` is just a label. The number 3797 isn't "bigger" than 464 in any meaningful way. So each ID is used to **look up a row** in a table.

### 7.1 Token embedding

A table with **16,384 rows** (one per token) and **512 columns**. Token 3797 → grab row 3797 → a vector of 512 numbers.

Tiny example with a vocabulary of 4 and a width of 3:
```
Embedding table E:            ids = [2, 0, 2]
row 0: [ 0.1,  0.5, -0.2]
row 1: [ 0.0, -0.3,  0.8]     lookup → [[ 0.7, 0.1, 0.4],   (row 2)
row 2: [ 0.7,  0.1,  0.4]               [ 0.1, 0.5,-0.2],   (row 0)
row 3: [-0.6,  0.2,  0.0]               [ 0.7, 0.1, 0.4]]   (row 2 again)
```

The table starts **random**. Through training, tokens with similar meanings ("cat", "dog") drift toward similar vectors.

### 7.2 Position embedding

Without help, the model can't tell `"dog bites man"` from `"man bites dog"`: same tokens, same vectors. So there's a **second table** with one row per **position** (512 rows × 512 columns). Position 0 gets row 0, position 1 gets row 1, and so on. These are **added** to the token vectors:

```
x = token_embedding[id] + position_embedding[position]
```

> 📁 **In the code:** `model.py:41`
> ```python
> x = self.tokens(ids) + self.positions(torch.arange(ids.size(1), device=ids.device))
> ```

> 💡 **Key idea:** Embedding = table lookup. Each token gets a learned "meaning vector", plus a learned "position vector".

> **Q: How many knobs are in the token embedding table? In the position table?**
>
> A: Token table: `16,384 × 512 = 8,388,608`. Position table: `512 × 512 = 262,144`.

## Chapter 8: The Linear layer

> 🧒 **ELI5:** A Linear layer takes a list of numbers and makes a new list. Each new number is made by multiplying every old number by its own weight and adding them all up. Training changes those weights.

The most common building block. It's the matrix multiplication from Chapter 2 plus an optional **bias** (a vector added at the end):

```
y = x @ W.T + b
```

- `W`: a weight matrix of shape `(out, in)`, the knobs.
- `b`: a bias vector of shape `(out,)`, more knobs (an adjustable "offset").
- Every output is a weighted mix of every input.

**The same `W` is applied to every token position independently.** If x is `(b, t, 512)` and W is `(2048, 512)`, then y is `(b, t, 2048)`, so every one of the b×t token vectors went through the same mixer.

> 📁 **In the code:** `nn.Linear(width, 4 * width)` and similar in `model.py`. Note `bias=False` on the attention linears: they skip the bias.

> 🧒 **ELI5, neurons:** people call each output number of a Linear layer a **neuron**. A neuron isn't a little brain cell inside the computer. It's one row of `W`, a recipe that says "take this much of input 1, this much of input 2, …, and add it all up". The weights in that row are its **connections**.

## Chapter 9: Activation functions (GELU)

> 🧒 **ELI5:** Multiplying and adding alone can only make straight-line patterns, no matter how many layers you stack. GELU is a simple function applied to every number: positive numbers mostly stay the same, and negative numbers get pushed close to zero. That small change lets the model learn more complicated patterns.

### 9.1 Why we need something that isn't a straight line

Stack two Linear layers with nothing in between:
```
y = W2 @ (W1 @ x) = (W2 @ W1) @ x = W_combined @ x
```
Two linears **collapse into one linear**. You could stack a thousand and it would still only be able to draw straight lines. To learn curvy, complicated patterns, you need a **non-linear** function in between. That's an **activation function**.

### 9.2 GELU

**GELU** = **G**aussian **E**rror **L**inear **U**nit. Roughly: *let positive numbers through, squash negative numbers toward zero, smoothly.*

```
GELU(x) = x · Φ(x)          Φ = "bell curve area to the left of x" (between 0 and 1)
```

| x | −3 | −2 | −1 | −0.5 | 0 | 0.5 | 1 | 2 | 3 |
|---|---|---|---|---|---|---|---|---|---|
| GELU(x) | −0.004 | −0.046 | −0.159 | −0.154 | 0 | 0.346 | 0.841 | 1.955 | 2.996 |

```
 GELU
  3 ┤                                  ╱
  2 ┤                              ╱
  1 ┤                        ╱
  0 ┼━━━━━━━━━━━━━━━━━━━━╮╱───────────────
    └──┬────┬────┬────┬────┬────┬────┬──
      -3   -2   -1    0    1    2    3
```

It's like a dimmer switch: big positive values pass almost unchanged, big negative values are almost blocked, and there's a smooth transition near zero.

> 💡 **Key idea:** Without activation functions, a deep network is just one big linear function. GELU is what lets it learn complicated shapes.

## Chapter 10: LayerNorm

> 🧒 **ELI5:** After many layers, the numbers can get too big or too small, and that makes training unstable. LayerNorm fixes this by adjusting each list of numbers so that its average is 0 and the numbers are spread out by about 1.

### 10.1 The problem

As numbers pass through many layers, they can drift. Some vectors get huge, others shrink to nothing, and training becomes unstable.

### 10.2 The fix

**LayerNorm** (Layer Normalization) rescales **each token's vector on its own** so it has an average of 0 and a spread (standard deviation) of 1. Then it applies a learned scale (`gamma`) and shift (`beta`), so the model can undo the normalization if it wants to.

```
mean  = average of the vector
var   = average of (value − mean)²          ("variance" = spread²)
xhat  = (x − mean) / sqrt(var + 0.00001)   (the tiny number prevents dividing by zero)
y     = gamma · xhat + beta
```

**Worked example:** `x = [1, 2, 3, 6]`
```
mean = (1+2+3+6)/4 = 3
var  = ((−2)² + (−1)² + 0² + 3²)/4 = (4+1+0+9)/4 = 3.5
sqrt(3.5) ≈ 1.871
xhat = [−2, −1, 0, 3] / 1.871 = [−1.069, −0.535, 0.000, 1.604]
```
With gamma = 1 and beta = 0 (their starting values), `y = xhat`. The relative pattern is kept, but the scale is now standard.

> 📁 **In the code:** `nn.LayerNorm(width)`. It appears before attention (`norm1`), before the MLP (`norm2`), and once at the very end (`self.norm`).

## Chapter 11: Attention, the heart of the transformer

> 🧒 **ELI5:** Each word needs information from other words. For example, to understand "it" in a sentence, the model needs to know what "it" refers to. Attention lets each word look at all the words before it, score how relevant each one is, and take in information mostly from the high-scoring ones. This is the only step where words share information with each other.

### 11.1 The problem attention solves

So far every token has been processed **alone**. But meaning depends on context:
- *"The **bank** of the river"* vs. *"The **bank** approved the loan"*
- *"Sarah lost **her** keys"*: to understand **her**, look back at **Sarah**.

**Attention** lets each token **look at earlier tokens and pull in information from the relevant ones.**

### 11.2 Query, Key, Value (QKV)

Each token makes three vectors from its own vector (via a Linear layer):

| Vector | Question it answers | Analogy (library search) |
|---|---|---|
| **Q**uery | "What am I looking for?" | what you type in the search bar |
| **K**ey | "What do I contain?" | the label on each book |
| **V**alue | "What info do I hand over?" | the book's actual contents |

The steps for one token:
1. Compare **its Query** with **every earlier token's Key** using a **dot product** (multiply matching entries and add them up). A high score means a good match.
2. Divide the scores by `sqrt(d)` (the **scaling**) so they don't get too large.
3. Turn the scores into percentages with **softmax** (Chapter 13). They add up to 100%.
4. Output = **weighted average of the Values**, weighted by those percentages.

### 11.3 Worked example: 3 tokens, width 2

To keep it simple, Q and K are the same, and `d = 2` so the scale is `sqrt(2) ≈ 1.414`.

```
          Q / K        V
token 1:  [1, 0]     [1, 0]
token 2:  [0, 1]     [0, 2]
token 3:  [1, 1]     [3, 3]
```

**Token 1** can only see itself (no peeking ahead):
- 100% on token 1 → output = `[1, 0]`

**Token 2** can see tokens 1 and 2:
- scores: `q2·k1 = 0·1 + 1·0 = 0`, `q2·k2 = 0·0 + 1·1 = 1` → scaled: `[0, 0.707]`
- softmax → `[0.33, 0.67]`
- output = `0.33·[1,0] + 0.67·[0,2]` = **`[0.33, 1.34]`**

**Token 3** can see tokens 1, 2 and 3:
- scores: `q3·k1 = 1`, `q3·k2 = 1`, `q3·k3 = 2` → scaled: `[0.707, 0.707, 1.414]`
- softmax → `[0.248, 0.248, 0.503]`
- output = `0.248·[1,0] + 0.248·[0,2] + 0.503·[3,3]` = **`[1.76, 2.01]`**

Token 3 "paid the most attention" to itself, because its query matched its own key best.

### 11.4 The causal mask: no cheating

> 🧒 **ELI5:** When the model is guessing a word, it is only allowed to look at the words before it, never the ones after. If it could see the next word, it would just copy it and not learn anything.

When training, the model is learning to predict the *next* token. If token 2 could look at token 3, it would just read the answer. So attention is **causal**: each token sees only itself and earlier tokens. Before softmax, future scores are set to **−∞** (minus infinity), and `exp(−∞) = 0` gives them 0% attention.

```
Attention pattern for 4 tokens (✓ = allowed):
           sees: t1  t2  t3  t4
token 1:         ✓   ·   ·   ·
token 2:         ✓   ✓   ·   ·
token 3:         ✓   ✓   ✓   ·
token 4:         ✓   ✓   ✓   ✓
```

> 🖥️ **See it on the dashboard: "03 / Inside attention: What can each token see?"**
>
> That grid is this exact table, drawn for your prompt. Each **row** is a token doing the looking (the **query**). Each **column** is a token being looked at (the **key**, the "Key position →" axis).
>
> - **Grey square = allowed:** the column's token comes at or before the row's token.
> - **Dark outlined square = future / hidden:** masked to −∞, so it gets 0% attention.
> - **Red square = the query you selected.** Row 1 ("The") can only see itself. Row 8 ("ets") can see all 8 tokens.
>
> The grey triangle always has the same shape, because it shows the **rule** for what's allowed, not what the model actually chose to look at. Inside the grey area, each of the 12 heads learns its own attention scores (Section 11.3). One head might put almost all its attention on a single earlier token.

### 11.5 Multiple heads

Instead of one attention with width 512, the model runs **8 attentions in parallel** (8 **heads**), each on a 64-number slice. Each head can specialize. One might track "which noun does this pronoun refer to?", another "what was the last verb?", another "what's the topic?". Their outputs are glued back together (8 × 64 = 512) and passed through one more Linear layer, the **projection**.

### 11.6 In the code

> 📁 `model.py:16-20`
> ```python
> b, t, c = x.shape
> q, k, v = self.qkv(self.norm1(x)).view(b, t, 3, self.heads, c // self.heads).permute(2, 0, 3, 1, 4).unbind(0)
> y = F.scaled_dot_product_attention(q, k, v, is_causal=True)
> x = x + self.proj(y.transpose(1, 2).contiguous().view(b, t, c))
> ```

Line by line:
- `self.qkv(...)` is **one** Linear layer producing Q, K and V together: `(b, t, 512) → (b, t, 1536)`.
- `.view(b, t, 3, 8, 64)` cuts those 1536 numbers into 3 (q/k/v) × 8 heads × 64.
- `.permute(2, 0, 3, 1, 4)` reorders the dimensions to `(3, b, 8, t, 64)` so each head is its own little attention problem.
- `F.scaled_dot_product_attention` (**SDPA**) does steps 1–4 from 11.2, fast. `is_causal=True` applies the mask.
- `.transpose(...).view(b, t, c)` glues the heads back together, and `self.proj` mixes them.
- `x + ...` is a residual connection (next chapter).

> 💡 **Key idea:** Attention = each token asks a question (Q), every earlier token advertises what it has (K), and the token collects a weighted mix of their contents (V). It's how information moves *between* tokens. It's the only place that happens.

> **Q: Why does attention use a causal mask during training?**
>
> A: Training asks every position to predict the *next* token. Without the mask, a position could look at the next token and copy it. That's cheating, and it learns nothing useful for real generation, where the future doesn't exist yet.
>
> **Q: If a query has a dot product of 0 with every key, what percentages does softmax give?**
>
> A: Equal: every score is 0 → all `exp(0)=1` → each visible token gets `1/n`. The output is the plain average of the visible Values.

## Chapter 12: MLP, residuals, and the full block

> 🧒 **ELI5:** The MLP is two Linear layers with GELU in between. It works on each word by itself, after attention has given that word information from the other words. A residual connection means each layer's result is added to its input instead of replacing it, so information from earlier layers isn't lost.

### 12.1 The MLP: thinking about what you gathered

**MLP** = **M**ulti-**L**ayer **P**erceptron (an old name for "a few linear layers with activations in between"). In each block:

```
512 numbers → Linear → 2048 numbers → GELU → Linear → 512 numbers
```

It widens 4×, squishes, and narrows back. Attention *moves* information between tokens. The MLP *processes* it within each token. Research suggests a lot of a model's factual knowledge is stored in these MLP weights.

> 🖥️ **See it on the dashboard: "A look inside: Neurons & connections"**
>
> The three columns of dots are **one block's MLP**, left to right:
>
> | Column | What it is | Full size in the `big` model |
> |---|---|---|
> | Input features | the numbers coming into the MLP for one token | 768 |
> | Hidden neurons | the outputs of Linear 1 (then GELU), the "widened" layer | 3,072 (= 4 × 768) |
> | Output features | the outputs of Linear 2, which the residual adds back | 768 |
>
> - **Each line is one weight.** It's a single number inside Linear 1's `W` (the left half of the picture) or Linear 2's `W` (the right half). Training adjusted every one of them.
> - **Red = positive weight, blue = negative weight.** Positive means "more of this input pushes this neuron up". Negative means "it pushes it down". Neither is "good" or "bad".
> - **Brighter = bigger magnitude** (size ignoring the sign). A brighter line has more influence.
> - **It's a sample, not the whole layer.** It draws 32 inputs, 48 hidden neurons and 32 outputs: 32×48 + 48×32 = 3,072 lines. The real Block 1 MLP has 768×3,072 + 3,072×768 ≈ 4.7 million weights, far too many to draw.
> - **It shows weights, not activity.** These lines are the fixed knobs from the latest saved checkpoint, so they stay the same whatever prompt you type. What does change with each prompt are the *values* flowing through them (the **activations**), and this panel doesn't draw those. Attention, biases, LayerNorm and residuals aren't drawn either.
> - **Block menu:** each of the 12 blocks has its own MLP with its own weights. Switch blocks and the pattern changes.
>
> 🧪 **Try it:** click a hidden neuron (a middle dot) and roughly count its red vs blue incoming lines. Then: if all 768 inputs were 1.0, what decides whether this neuron's total comes out positive or negative? (Answer: the sum of all 768 of its incoming weights, plus its bias.)

### 12.2 Residual connections: the shortcut

Instead of `x = layer(x)`, every block does:
```
x = x + layer(x)
```
The layer only has to learn a **correction** to add, not rebuild everything from scratch. Think of 8 editors each making small notes on the same document, instead of each one rewriting it.

There's a second big benefit you'll see in Chapter 14: during backprop, the `+` acts as a **highway**. The learning signal can flow straight back through all 8 blocks without fading out.

### 12.3 One complete block

> 📁 `model.py:16-21`, rewritten with names:
```
h1 = LayerNorm1(x)
x1 = x  + Attention(h1)          ← residual #1
h2 = LayerNorm2(x1)
x2 = x1 + MLP(h2)                ← residual #2
```
This "normalize, then do the thing, then add back" pattern is called **pre-norm**.

## Chapter 13: The output. Logits, softmax and the loss

> 🧒 **ELI5:** The model gives each possible next token a score. Softmax turns the scores into chances that add up to 100%. The loss measures how much chance the model gave the correct token. More chance on the right answer means a lower loss, which is good.

### 13.1 Logits

After the final LayerNorm, each position has a 512-number vector. To score every possible next token, the model compares that vector against **every row of the token embedding table** (dot product). That gives 16,384 raw scores, called **logits**. A higher logit means "more likely next".

**Tied embeddings:** the *same* table is used to read tokens in and to score tokens out. That saves 8.4 million knobs and makes sense: a token's meaning vector is useful in both directions.

> 📁 `model.py:43`: `return F.linear(self.norm(self.blocks(x)), self.tokens.weight)`

### 13.2 Softmax: scores → probabilities

```
p_i = exp(z_i) / (sum of exp(z_j) for all j)
```
`exp` makes everything positive, and dividing by the total makes them add up to 1.

**Worked example**, with a vocabulary of 3 and logits `z = [2.0, 1.0, 0.1]`:
```
exp:  [7.389, 2.718, 1.105]     total = 11.212
p:    [0.659, 0.242, 0.099]     (adds to 1.0)
```

### 13.3 Cross-entropy loss: grading the guess

```
loss = −log( probability given to the correct token )
```

If the correct token was #0 (probability 0.659): `loss = −log(0.659) = 0.417`.

| Probability given to the right answer | Loss |
|---|---|
| 100% | 0.00 (perfect) |
| 70% | 0.36 |
| 50% | 0.69 |
| 10% | 2.30 |
| 1% | 4.61 |
| 1/16,384 (pure random guess) | **9.70** |

The loss for a whole batch is the **average** over all positions.

**This table tells you how to read your training charts.** A brand-new random model starts near **9.7**. A loss of 3.0 means that on average the model gives the right token about `e^(−3) ≈ 5%`. That sounds low, but it's picking from 16,384 options, and often several continuations are reasonable.

> 💡 **Key idea:** The model outputs logits → softmax turns them into probabilities → cross-entropy grades how much probability went to the right answer. That single average number is "the loss".

> **Q: Logits `[0, 0, 0]`: what are the probabilities? What's the loss if the answer is token #1?**
>
> A: All equal: `[1/3, 1/3, 1/3]`. Loss = `−log(1/3) = log 3 ≈ 1.10`.

# PART 4: How It Learns

## Chapter 14: Backpropagation

> 🧒 **ELI5:** Backpropagation works out, for every number in the model, how much it contributed to the error. It starts at the error and works backward through each step of the calculation, one step at a time. Those amounts are what tell us which way to change each number.

This is the most important chapter. Take it slowly.

### 14.1 The problem

After a forward pass, we have one number: the loss. We have 34 million knobs. For **each** knob we need its **gradient**: "if I nudge this knob up a bit, does the loss go up or down, and by how much?"

The slow way: nudge each knob one at a time and re-run the whole model. That's 34 million forward passes for **one** training step. Impossible.

**Backpropagation ("backprop")** gets *all* 34 million gradients for the cost of about **one extra pass** (roughly 2× a forward pass). It's the algorithm that makes deep learning possible.

### 14.2 The chain rule

> 🧒 **ELI5:** If changing A by 1 changes B by 3, and changing B by 1 changes C by 2, then changing A by 1 changes C by 3 × 2 = 6. When steps are connected one after another, you multiply their effects. Backpropagation is just this rule applied over and over.

If A affects B, and B affects C, then:
```
(how much A affects C) = (how much A affects B) × (how much B affects C)

         dC/dA        =       dB/dA          ×        dC/dB
```

**Everyday example:** each chore earns you $2, and each dollar buys 3 candies. How many candies per chore? `2 × 3 = 6`. You just used the chain rule.

### 14.3 The computation graph

Any calculation can be drawn as a chain of simple steps. Take a tiny 2-knob "network":
```
h = w1 · x
y = w2 · h
L = (y − target)²
```
```
  x ──┐
      ├─[×]──► h ──┐
  w1 ─┘            ├─[×]──► y ──[ (y−target)² ]──► L
              w2 ──┘
```

### 14.4 Worked example: forward, then backward

**Values:** `x = 1`, `w1 = 2`, `w2 = 3`, `target = 10`.

**Forward pass** (left to right), *saving every intermediate value*:
```
h = 2 · 1 = 2
y = 3 · 2 = 6
L = (6 − 10)² = 16
```

**Backward pass** (right to left). We write `dL/d(something)` as **`d_something`**, the "blame" on that thing.

1. **Start at the loss.** `d_L = 1` (the loss affects itself 1-to-1).

2. **Through the square:** `L = (y − 10)²` has local derivative `2(y − 10) = 2(−4) = −8`.
   `d_y = d_L × (−8) = −8`
   *Meaning: raising y would lower the loss.*

3. **Through `y = w2 · h`.** This step has two inputs, so it sends blame to both:
   - local derivative w.r.t. `w2` is `h = 2` → `d_w2 = d_y × h = −8 × 2 = −16`
   - local derivative w.r.t. `h` is `w2 = 3` → `d_h = d_y × w2 = −8 × 3 = −24`

4. **Through `h = w1 · x`:**
   - local derivative w.r.t. `w1` is `x = 1` → `d_w1 = d_h × x = −24 × 1 = −24`

**Result:** `d_w1 = −24`, `d_w2 = −16`. Both negative, so increasing either knob lowers the loss. That makes sense, since y = 6 is too small.

**Verify by nudging** (finite difference): set `w1 = 2.001` → `h = 2.001`, `y = 6.003`, `L = (−3.997)² = 15.976`.
Change in L / change in w1 = `(15.976 − 16) / 0.001 = −24`. ✔ It matches.

### 14.5 What just happened, in general

```
FORWARD  (compute + save notes):   x ──► h ──► y ──► L
BACKWARD (pass the blame back):    x ◄── h ◄── y ◄── L
```

Each step (each "node") only needs to know **its own local rule**:
> "Given the blame on my **output**, compute the blame on each of my **inputs** (and on my knobs)."

```
d_input = d_output × (local derivative)
```

Chain these local rules from the loss back to the start, and every knob gets its gradient. The model can have any number of steps, and each one only needs its small local rule. That's backprop.

**The "telephone line" picture:** a line of people passes a message, and the final answer is wrong. The teacher tells the last person how wrong it was. Each person works out "how much of this was my fault, and how much came from the person before me?", keeps their own share (their knob's gradient), and passes the rest back.

### 14.6 The two "add it up" rules

These cause most backprop bugs, so learn them now.

**Rule 1: If a value is used in two places, its blames ADD.**
```
        ┌──► f(x) ──┐
  x ────┤           ├──► out = x + f(x)       (a residual connection!)
        └───────────┘
  d_x = d_out (through the shortcut)  +  d_x (back through f)
```
Why: nudging x changes the output *through both paths*, so both effects count.

**Rule 2: If a knob is used at many positions, its blames ADD.**
The same weight matrix W is used for all 512 tokens. Each position contributes some gradient to W, and W's total gradient is the **sum** over all positions (and over the batch).

In your model:
- Residuals → Rule 1 (twice per block).
- Token embedding table used at the input **and** the output head → Rule 1.
- Every Linear layer → Rule 2.

### 14.7 Why the forward pass saves notes

Look at step 3 above: computing `d_w2` needed `h`, and computing `d_h` needed `w2`. The backward pass needs values from the forward pass. So during the forward pass, each step **caches** (saves) what it will need later. This is why training uses much more memory than generating text: all those notes must be held until the backward pass is done.

### 14.8 What PyTorch does for you

In `train.py`, all of this happens in one line:
```python
scaler.scale(value / args.accum).backward()
```
PyTorch secretly records every operation during the forward pass (that recording *is* the computation graph). `.backward()` walks it in reverse, applies each operation's built-in local rule, and stores each knob's gradient in `knob.grad`. This is called **autograd** (automatic differentiation).

In Part 5 you'll replace that one line with your own code.

> 💡 **Key idea:** Backprop = the chain rule applied systematically from the loss backward. Each operation knows only its local rule. Blames multiply along a path and add where paths merge.

> 🧪 **Try it 14.1:** Same graph, but `x = 2`, `w1 = 1`, `w2 = 4`, `target = 5`. Do the forward pass, then compute `d_w1` and `d_w2` by hand. Check `d_w1` by nudging w1 to 1.001.

> **Q: In `out = x + f(x)`, if `d_out = 5` and the blame coming back through `f` is `2`, what is `d_x`?**
>
> A: `d_x = 5 + 2 = 7`. Both paths add (Rule 1).

## Chapter 15: The backward rule for every layer

> 🧒 **ELI5:** Each type of layer needs its own backward rule. The rule says: given how much this layer's output affected the error, here's how much each of its inputs and weights affected the error. Once every layer has its rule, you run them in reverse order, from the last layer to the first.

Now we go through each layer in your model and write its backward rule. For each one you'll get: **what it does → its rule in words → the formula → shapes.**

Notation: `dX` means "the gradient of the loss with respect to X". **`dX` always has the same shape as `X`.** That's your number-one bug check.

The order below is the order the backward pass runs, **from the loss back to the input**.

### 15.1 Softmax + cross-entropy (the starting point)

**Forward:** logits `z` → `p = softmax(z)` → `loss = −log p[target]`.

**Backward rule:**
```
dz = p − onehot(target)
```
where `onehot(target)` is a vector of zeros with a 1 at the correct token.

**Worked example:** `z = [2.0, 1.0, 0.1]`, `p = [0.659, 0.242, 0.099]`, target = 0:
```
dz = [0.659 − 1, 0.242 − 0, 0.099 − 0] = [−0.341, 0.242, 0.099]
```
In words: **push the right answer's score up** (negative gradient → the update raises it), and **push every wrong answer's score down**, in proportion to how much probability it wrongly got. That's a very intuitive rule.

**Why it's this simple** (optional derivation):
`loss = −z_target + log(Σ exp(z_j))`. The derivative of the first term w.r.t. `z_i` is `−1` if i is the target (else 0). The derivative of the second term is `exp(z_i)/Σexp(z_j) = p_i`. Adding them gives `p_i − 1[i = target]`.

**Averaging:** the loss is the mean over N graded positions, so divide by N: `dz = (p − onehot) / N`.

**Ignored positions:** in dialogue training (Chapter 19), positions labeled `-100` aren't graded, so their gradient is 0 and they don't count in N.

Shapes: `dlogits` is `(b, t, V)`, the same as the logits.

### 15.2 Linear layer

**Forward:** `y = x @ W.T + b`, with x `(…, in)`, W `(out, in)`, b `(out,)`, y `(…, out)`.

**Backward rules:**
```
dx = dy @ W                    blame flows back through the same weights
dW = dy.T @ x                  (flatten all positions first, sums over them: Rule 2)
db = dy summed over positions
```

**Intuition:** `y[j] = Σ_i W[j,i]·x[i] + b[j]`.
- W[j,i] multiplies x[i], so `dW[j,i] = dy[j]·x[i]`. ("This knob mattered as much as its input was large.")
- x[i] feeds *every* output j, so `dx[i] = Σ_j dy[j]·W[j,i]`. (Rule 1: x[i] is used in many places, so the blames add.)
- b[j] is added directly, so `db[j] = dy[j]`.

**Worked example** (W from Chapter 2, `x = [1, 2]`, and suppose `dy = [1, 0, −1]`):
```
dx = dy @ W = [1·1 + 0·0 + (−1)·1,  1·0 + 0·1 + (−1)·1] = [0, −1]
dW = outer(dy, x) = [[ 1,  2],
                     [ 0,  0],
                     [−1, −2]]
db = [1, 0, −1]
```
**Shape check:** dx `(2,)` = x ✔, dW `(3, 2)` = W ✔, db `(3,)` = b ✔.

### 15.3 GELU

**Forward:** `y = GELU(x)`, applied to each number separately.

**Backward rule:** each output depends only on its own input, so just multiply by the local slope:
```
dx = dy × GELU'(x)          where GELU'(x) = Φ(x) + x·φ(x)
```
Φ is the bell-curve area to the left (the CDF), φ is the bell-curve height (the PDF): `φ(x) = exp(−x²/2)/sqrt(2π)`.

| x | −2 | −1 | 0 | 1 | 2 |
|---|---|---|---|---|---|
| GELU′(x) | −0.085 | −0.083 | 0.5 | 1.083 | 1.085 |

So for big positive inputs the gradient passes through (slope ≈ 1). For big negative inputs it's nearly blocked (slope ≈ 0).

### 15.4 Residual connection

**Forward:** `out = x + f(x)`.
**Backward:** copy `d_out` straight to `x` **and** send it through `f`'s backward, then **add** the results (Rule 1):
```
dx = d_out + (f's backward applied to d_out)
```
This is the "gradient highway". Even if `f` squashes the gradient, the `d_out` term passes through untouched.

### 15.5 LayerNorm

**Forward** (per token vector of size c): `xhat = (x − mean)·rstd`, `y = gamma·xhat + beta`, where `rstd = 1/sqrt(var + eps)`.

**Backward rules:**
```
dgamma = sum over positions of (dy × xhat)
dbeta  = sum over positions of dy
dxhat  = dy × gamma
dx     = rstd × ( dxhat − mean(dxhat) − xhat × mean(dxhat × xhat) )
```
(The `mean`s are across the c numbers of each token.)

**Why three terms?** Each input `x[i]` affects the output in three ways:
1. **Directly**: it's part of `x − mean` → the `dxhat` term.
2. **Through the mean**: changing x[i] shifts the mean, which shifts *every* xhat → the `− mean(dxhat)` term.
3. **Through the spread**: changing x[i] changes var, which rescales *every* xhat → the `− xhat × mean(dxhat × xhat)` term.

Three paths, three terms, added up. That's Rule 1 again.

> 🧪 **Try it 15.1 (challenge):** Derive the LayerNorm formula yourself on paper for a vector of size 2. It's the best chain-rule exercise in the whole model.

### 15.6 Softmax (inside attention)

Inside attention we need softmax's backward rule on its own (not combined with cross-entropy):
```
P  = softmax(S)                      (along each row)
dS = P × ( dP − sum(dP × P) )        (sum along each row)
```
**Why:** each probability depends on *all* the scores (raising one score lowers every other probability). The `sum(dP × P)` term accounts for that "competition".

### 15.7 Attention

**Forward** (per head):
```
qkv = x @ Wqkv.T             then cut into q, k, v       (b, h, t, d) each
S   = q @ k.T / sqrt(d)                                  (b, h, t, t)
S   = mask future with −∞
P   = softmax(S)                                         (b, h, t, t)
Y   = P @ v                                              (b, h, t, d)
out = merge heads(Y) @ Wproj.T                           (b, t, c)
```

**Backward:** run the steps in reverse, applying the rules you already know:
```
1. Projection (a Linear):     dmerged, dWproj   = linear_backward(dout)
2. Un-merge heads:            dY = reshape dmerged back to (b, h, t, d)
3. Y = P @ v  (two inputs):   dv = P.T @ dY
                              dP = dY @ v.T
4. Softmax:                   dS = P × (dP − sum(dP × P))
   (masked spots had P = 0, so their dS = 0 automatically)
5. S = q @ k.T / sqrt(d):     dq = dS @ k   / sqrt(d)
                              dk = dS.T @ q / sqrt(d)
6. Re-pack dq, dk, dv into one (b, t, 3c) tensor, undoing the view/permute
7. QKV (a Linear):            dx, dWqkv = linear_backward(dqkv)
```

Notice that **step 3 and step 5 are just the matrix multiplication rule** from the Linear layer (`y = a @ b` → `da = dy @ b.T`, `db = a.T @ dy`). Attention is mostly matrix multiplies, softmaxes and reshapes, and you already know all three rules.

**The reshape trap:** the forward pass did `.view(b, t, 3, h, d).permute(2, 0, 3, 1, 4)`. In the backward pass you must exactly undo that: stack `[dq, dk, dv]` into `(3, b, h, t, d)`, then `.permute(1, 3, 0, 2, 4)` back to `(b, t, 3, h, d)`, then reshape to `(b, t, 3c)`. Reshapes don't change values, only where they sit, so their "backward" is just the reverse reshape.

### 15.8 Embeddings (the end of the line)

**Forward:** `x = E[ids] + Pos[0..t−1]`.

**Backward:** a lookup copies rows, so the backward pass **adds blame back into those rows**:
```
for every position (n, i):
    dE[ ids[n,i] ] += dx[n, i]          ← "scatter-add"
dPos[i] += sum over batch of dx[:, i]
```
If the token "the" appears 30 times in the batch, row "the" collects 30 contributions (Rule 2). Rows of tokens that didn't appear get zero.

**Tied embeddings:** `E` *also* got gradient from the output head (`logits = xf @ E.T` → `dE = dlogits.T @ xf`). Both contributions **add** (Rule 1). Forgetting this is the classic bug.

### 15.9 The whole backward pass, in order

```
loss
 └─► dlogits = (p − onehot) / N                         [15.1]
      ├─► dE   += dlogits.T @ xf    (tied head)         [15.2 + Rule 1]
      └─► dxf  = dlogits @ E
           └─► final LayerNorm backward → dx             [15.5]
                for block = 8, 7, …, 1:
                  MLP:  Linear2 → GELU → Linear1 → LN2   [15.2, 15.3, 15.5]
                  dx1 = dx + (that result)               [15.4]
                  Attn: proj → attention → qkv → LN1     [15.7, 15.5]
                  dx  = dx1 + (that result)              [15.4]
           └─► dE[ids] += dx;  dPos += dx                [15.8]
```

> **Q: In a Linear layer, if `x` is shape `(2, 10, 16)` and `W` is `(32, 16)`, what are the shapes of `dy`, `dx` and `dW`?**
>
> A: `dy`: `(2, 10, 32)`. `dx`: `(2, 10, 16)`, same as x. `dW`: `(32, 16)`, same as W.
>
> **Q: Why does the token embedding get gradient from two places?**
>
> A: It's used twice: once as the input lookup table, and once as the output head that scores every token (tied embeddings). By Rule 1, both gradients add.

## Chapter 16: Gradient checking (how to know your backprop is right)

> 🧒 **ELI5:** To check your backpropagation, change one weight by a tiny amount and see how much the error really changes. Then compare that with what your code calculated. If the two numbers match, your code is correct.

Backprop code can be *wrong* and still run. The loss might even go down, just slower. So you **must** check it. There are two ways.

### 16.1 Compare against autograd (best)

PyTorch's autograd is your **answer key**. Run the same inputs and weights through both and compare:

```python
def check(name, mine, ref, tol=1e-8):
    err = (mine - ref).abs().max().item()
    rel = err / (ref.abs().max().item() + 1e-12)
    print(f"{'OK ' if rel < tol else 'BAD'} {name:28s} rel_err={rel:.1e}")
```

### 16.2 Finite differences (works for anything)

Nudge one knob and measure (Chapter 2.5):
```python
eps = 1e-6
w[i] += eps;     loss_plus  = forward(...)
w[i] -= 2*eps;   loss_minus = forward(...)
w[i] += eps
numeric_grad = (loss_plus - loss_minus) / (2 * eps)
```
It's slow (two forward passes per knob), so only spot-check a few knobs.

### 16.3 Tips that save hours

1. **Use float64** (`torch.set_default_dtype(torch.float64)`). In 32-bit or 16-bit, rounding noise hides real bugs.
2. **Use tiny sizes**: width 16, 2 layers, 2 heads, vocab 50. Runs instantly, and you can print things.
3. **Test each layer alone** before assembling. To test one layer, make a random "fake upstream gradient" `dout`, then `(layer(x) * dout).sum().backward()` gives autograd's answer for that exact `dout`.
4. **Initialize weights larger than usual** in tests (e.g. std 0.3). With tiny weights some bugs produce tiny errors that slip under the tolerance.
5. **The usual suspects:** a missing transpose, `mean` vs `sum`, forgetting `+=` (Rules 1 and 2), and undoing a permute in the wrong order.

## Chapter 17: The training loop

> 🧒 **ELI5:** Training repeats the same steps many times: take some text, let the model guess the next tokens, measure the error, use backpropagation to find how each weight affected it, and change the weights a little. Every so often, test the model on text it has never trained on to check it's really improving.

> 📁 **In the code:** `train.py`, lines 129–167. Let's walk through each piece.

### 17.1 Making a batch: inputs and answers

Grab **513** consecutive tokens. The input is tokens 1–512, the answers are tokens 2–513:

```
tokens:  [The] [cat] [sat] [on] [the] [mat]
input:   [The] [cat] [sat] [on] [the]
answer:  [cat] [sat] [on]  [the] [mat]
```
One chunk of 512 tokens = **512 prediction quizzes** at once. (`train.py:97`: `return data[:, :-1], data[:, 1:]`)

**Batch:** process several chunks at once (`--batch 2`). The GPU (**G**raphics **P**rocessing **U**nit) is great at doing many things in parallel.

**Epoch:** one full pass through all the training data. The **block sampler** (`training_utils.py`) cuts `train.bin` into 512-token blocks and visits every block once per epoch, in a shuffled order.

### 17.2 Forward + loss + backward

```python
logits = model(x)
loss = F.cross_entropy(logits.reshape(-1, V), y.reshape(-1))
loss.backward()      # ← backprop; fills every knob's .grad
```

### 17.3 Gradient accumulation

The GPU's memory (**VRAM**, **V**ideo **RAM**; 12 GB on the RTX 4070 Ti) only fits 2 chunks at a time. But bigger batches give steadier, less noisy gradients. Solution:

```python
opt.zero_grad()                       # clear old gradients
for _ in range(8):                    # --accum 8
    loss = compute_loss(next_batch)
    (loss / 8).backward()             # gradients ADD into .grad
opt.step()                            # one update using the summed gradient
```
Result: identical to a batch of 16 chunks = **2 × 8 × 512 = 8,192 tokens per update step**. Dividing by 8 makes it an average instead of a sum.

### 17.4 Gradient clipping

Occasionally a weird batch produces a huge gradient that would throw the knobs far off course. **Clipping** measures the total length of the gradient (all 34M numbers treated as one long arrow). If it's longer than 1.0, it's scaled down to length 1.0, keeping the same direction:
```python
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
```

### 17.5 The optimizer: AdamW

> 🧒 **ELI5:** AdamW is the rule that decides how much to change each weight. It keeps track of the recent direction for each weight and keeps moving that way. If a weight's direction keeps changing a lot, it takes smaller steps for that weight. It also shrinks all weights slightly each step so none get too large.

Plain gradient descent (**SGD**, Stochastic Gradient Descent; *stochastic* means "using random samples") does `w = w − lr × grad`. Your project uses **AdamW**, which adds three upgrades:

1. **Momentum** (the "first moment" `m`): a running average of recent gradients. Like a ball rolling downhill, it keeps moving in a consistent direction and smooths out jitter.
   `m = 0.9·m + 0.1·grad`
2. **Adaptive step size** (the "second moment" `v`): a running average of *squared* gradients, tracking how big and noisy each knob's gradient usually is. Each knob's step is divided by `sqrt(v)`, so every knob effectively gets its own learning rate.
   `v = 0.999·v + 0.001·grad²`
3. **W = decoupled Weight decay** (0.1 here): each step, shrink every knob slightly toward zero: `w = w − lr·0.1·w`. This keeps knobs from growing huge, which helps the model generalize instead of memorize.

(There's also a "bias correction" that divides m and v by `(1 − 0.9^step)` and `(1 − 0.999^step)`, because they start at 0 and would otherwise be too small early on.)

**Worked first step:** `w = 1.0`, `grad = 0.5`, `lr = 0.001`:
```
decay:  w = 1.0 − 0.001·0.1·1.0          = 0.9999
m = 0.1 · 0.5   = 0.05     → corrected: 0.05 / (1 − 0.9)     = 0.5
v = 0.001·0.25  = 0.00025  → corrected: 0.00025 / (1 − 0.999) = 0.25
step = lr · 0.5 / sqrt(0.25) = 0.001 · 0.5 / 0.5 = 0.001
w = 0.9999 − 0.001 = 0.9989
```
Interesting fact: on step 1, Adam moves every knob by about **±lr**, regardless of how big the gradient is. Only the direction matters at first.

**"Fused"** (`--optimizer-backend fused`) is a faster implementation that updates all knobs in one GPU operation. Same math.

### 17.6 The learning-rate schedule: warmup + cosine

> 🧒 **ELI5:** The step size isn't fixed. It starts small for the first steps, rises to its biggest value, and then slowly gets smaller until the end of training. Starting small avoids big mistakes early on, and ending small lets the model settle.

> 📁 `training_utils.py`, `learning_rate()`

```
 LR
3e-4 ┤      ╭──╮
     │     ╱    ╲
     │    ╱      ╲__
1.5e-4┤  ╱           ╲___
     │  ╱                ╲____
3e-5 ┤ ╱                      ╲________________________
     └┬────┬──────────────────────────────┬────────────► step
      0   200                           10,000
      warmup         cosine decay            (stays at min)
```

| Step | 1 | 100 | 200 | 2,650 | 5,100 | 7,550 | 10,000 | 12,000 |
|---|---|---|---|---|---|---|---|---|
| LR | 1.5e-6 | 1.5e-4 | **3.0e-4** (peak) | 2.6e-4 | 1.65e-4 | 7.0e-5 | **3.0e-5** (min) | 3.0e-5 |

- **Warmup** (steps 0–200): the knobs start random and AdamW's averages are empty, so big steps right away could be chaotic. The LR ramps up gradually.
- **Cosine decay** (200–10,000): slide down along half a cosine wave. Take big steps early to make fast progress, and small steps late to settle into a good spot.

(The `e` notation: `3e-4` = 3 × 10⁻⁴ = 0.0003.)

### 17.7 Mixed precision (AMP)

Numbers can be stored with different precision:

| Format | Bits | Precision | Speed |
|---|---|---|---|
| **fp32** (32-bit float) | 32 | high | slower |
| **fp16** (16-bit float) | 16 | low, small range | fast |
| **bf16** ("brain float", 16-bit) | 16 | low, but same *range* as fp32 | fast |

**AMP** (**A**utomatic **M**ixed **P**recision) does the heavy math in 16-bit and keeps the knobs and sensitive steps in 32-bit. `train.py` uses bf16 when the GPU supports it, which your RTX card does.

The **GradScaler** is only needed for fp16. Tiny gradients can round to 0 in fp16, so the loss is temporarily multiplied by a large number before backward, and the gradients are divided back down before the update. With bf16 it does nothing.

### 17.8 Validation and overfitting

> 🧒 **ELI5:** We test the model on text it never trained on. If the model keeps getting better on its training text but worse on this new text, it is memorizing instead of learning. That's called overfitting.

Every 50 steps (`--eval-every`), `train.py` computes the loss on **val** data, which the model never trained on:

```
loss
  │╲
  │ ╲   train loss
  │  ╲___________________
  │   ╲     val loss    ____╱‾‾‾ ← val rising while train falls = OVERFITTING
  │    ╲_______________╱           (memorizing, not learning)
  └──────────────────────────────► steps
```
If val loss tracks train loss, the model is learning real patterns. If val loss starts **rising** while train loss keeps **falling**, it's memorizing the training data. That's **overfitting**.

### 17.9 Checkpoints

At each evaluation, `train.py` saves `latest.pt` (a **checkpoint**) containing:
- the model knobs
- AdamW's memory (m and v for every knob)
- the step number
- the random-number-generator states (so a resumed run makes *exactly* the same choices)

It writes to a temporary file first and then renames it, so a crash mid-save can never corrupt the checkpoint. `--resume` picks up exactly where it left off.

> 💡 **Key idea:** One training step = (accumulate gradients over several small batches) → clip → AdamW update with the scheduled learning rate. Do this thousands of times and check val loss along the way.

> **Q: With `--batch 4 --accum 4 --context 512`, how many tokens are in one update step?**
>
> A: `4 × 4 × 512 = 8,192` tokens.
>
> **Q: Why does training start with a small learning rate (warmup) instead of the peak right away?**
>
> A: At the start the knobs are random and AdamW has no gradient history, so early gradients are unreliable. Big steps could push the model into a bad, unstable region. Warming up lets things settle before taking big steps.

## Chapter 18: Generating text

> 🧒 **ELI5:** To write text, the model picks the next token at random, but tokens with higher chances get picked more often. Temperature changes this: low temperature makes it almost always pick the most likely token, and high temperature makes less likely tokens get picked more often.

> 📁 `generate.py`, lines 47–56

```
1. Encode the prompt → token IDs
2. Run the model → logits for the LAST position only
3. Divide logits by the temperature
4. Keep only the top 50 (top-k); set the rest to −∞
5. Softmax → probabilities
6. Randomly pick a token, weighted by the probabilities
7. If it's <eos>, stop. Otherwise append it and go to step 2.
```

### 18.1 Temperature

> 🧒 **ELI5:** Temperature is a "boldness" knob for picking the next word. Turn it down and the model plays it safe, picking its favourite word almost every time. Turn it up and it takes more chances on words it rated lower, which makes it more surprising but also more likely to talk nonsense.

**What it changes:** only how the next token is *picked*. Temperature doesn't change the model, its weights or what it knows. It's applied after the model has done its work and handed back its logits (Chapter 13), so you can change it on every request for free.

**The rule:** divide every logit by the temperature `T`, then do softmax as usual.

```
probabilities = softmax(logits / T)
```

#### Worked example

Say there are only 3 possible next tokens, with logits `[2.0, 1.0, 0.1]`. Here's every step at **T = 0.5** and at **T = 2.0**, using softmax from Section 13.2: `exp` each number, then divide each by their total.

| Step | T = 0.5 | T = 2.0 |
|---|---|---|
| 1. Divide each logit by T | [4.0, 2.0, 0.2] | [1.0, 0.5, 0.05] |
| 2. `exp` each one | [54.60, 7.39, 1.22] | [2.72, 1.65, 1.05] |
| 3. Add them up | 63.21 | 5.42 |
| 4. Divide each by the total | **[0.864, 0.117, 0.019]** | **[0.502, 0.304, 0.194]** |

**Why it works:** dividing by a number **below 1** makes the gaps between logits **bigger** (2.0 vs 1.0 is a gap of 1; after dividing by 0.5 it's 4.0 vs 2.0, a gap of 2). `exp` turns bigger gaps into much bigger ratios, so the top token takes almost everything. Dividing by a number **above 1** shrinks the gaps, so the probabilities move closer together.

The same logits at more temperatures:

| Temperature | Probabilities | Effect |
|---|---|---|
| 0.1 | [1.000, 0.000, 0.000] | almost always the top token ("greedy") |
| 0.5 | [0.864, 0.117, 0.019] | sharper: safe, can get repetitive |
| 0.7 | [0.766, 0.184, 0.051] | a bit sharper: used by the dashboard chat |
| 0.8 (default) | [0.725, 0.208, 0.067] | slightly sharpened |
| 1.0 | [0.659, 0.242, 0.099] | the model's real beliefs, unchanged |
| 2.0 | [0.502, 0.304, 0.194] | flatter: creative, chaotic |

Two things the table shows:
- **The order never changes.** The token with the highest logit always has the highest probability at every temperature. Temperature only changes *how much more likely* it is.
- **T = 1 does nothing,** because dividing by 1 leaves the logits as they are. **As T gets close to 0,** sampling turns into always picking the top token, which is called **greedy decoding**. T can't be exactly 0, since you can't divide by zero, so `generate.py` only accepts **0.1 to 2**.

> 🔥 **Why is it called "temperature"?** It's the same temperature as in physics, and the math is the same formula. In physics, the **Boltzmann distribution** gives the chance that a molecule sits in a state with a certain energy:
>
> ```
> chance of a state ∝ exp(−energy / temperature)
> ```
>
> (`∝` means "is proportional to": you still divide by the total so the chances add up to 1, just like softmax.) Softmax with temperature is exactly this, with **logit = −energy**:
>
> ```
> chance of a token ∝ exp(logit / T)
> ```
>
> A high logit is like a low-energy, "comfortable" state.
>
> - **Cold:** the energy gaps matter a lot, so almost every molecule settles into the lowest-energy state (ice: molecules locked in place). The model "freezes" onto its top token.
> - **Hot:** the gaps matter less, so molecules spread across many states, even high-energy ones (steam: chaotic). The model "boils" and hops between many tokens.
>
> AI borrowed the name because softmax came straight from statistical physics, where this formula had been used for about a century before neural networks existed.

#### Choosing a temperature

| Task | Good range | Why |
|---|---|---|
| Answering from library passages | 0.3–0.7 | You want the answer copied faithfully from the passage, not invented |
| Normal chat | 0.7–0.9 | Natural wording without drifting off topic |
| Stories, brainstorming | 0.9–1.2 | More variety, more surprising word choices |
| Above about 1.3 | rarely useful | Small models start producing word salad |

Low temperatures have their own failure: a small model at 0.3 often **loops**, repeating the same phrase, because its top choice after "the city of the city of" is again "the city of". If you see repetition, raise the temperature a little.

> 🖥️ **See it on the dashboard:** the **Try** page has a temperature menu: **0.5 / focused**, **0.8 / balanced** (default), **1.1 / varied**. Use the same prompt and the same checkpoint and try all three; the higher one will wander more. The **Chat** page always uses **0.7**.

> 📁 **In the code:** `generate.py`, line 51 divides by the temperature right after the model runs:
> ```python
> logits = model(x[:, -model.config['context']:])[:, -1, :] / args.temperature
> ```
> Then top-k (next section) and softmax are applied to these divided logits.

> 🧪 **Try it:** with logits `[3.0, 1.0]`, work out the probabilities at T = 1 and at T = 0.5. How many times more likely is the first token in each case? (Answer: T = 1 gives [0.881, 0.119], so 7.4 times more likely, which is e² ≈ 7.39. T = 0.5 gives [0.982, 0.018], so 54.6 times more likely, e⁴ ≈ 54.6. Halving the temperature squared the ratio.)

> **Q: Does a lower temperature make the model smarter?**
>
> A: No. It only makes it pick its existing favourite more often. If the model's favourite is wrong, a low temperature makes it wrong more consistently.

### 18.2 Top-k

Even unlikely tokens have some tiny probability, and across 16,384 tokens those tiny chances add up. Sometimes a garbage token would get picked. **Top-k = 50** throws away everything except the 50 most likely candidates.

### 18.3 Context window

The model can only see a fixed number of tokens: 512 for the original model, 1,024 for the `big` one. When the text gets longer, `generate.py` feeds only the **last** 512 or 1,024 (`x[:, -context:]`). The model completely forgets anything earlier.

## Chapter 19: From text predictor to chat

> 🧒 **ELI5:** After training on Wikipedia, the model can only continue text that looks like Wikipedia. To make it answer questions, we train it more on example conversations between a user and an assistant. It's the same next-word guessing, just practiced on conversations.

> 📁 `dialogue.py`, `train_dialogue.py`

After Wikipedia **pre-training**, the model knows language and facts, but it only knows how to *continue articles*. The **dialogue stage** (also called **fine-tuning**: more training, on different data) teaches the *shape* of a conversation:

```
User: what's the capital of France?
Assistant: Paris.<eos>
```

The key trick is **labels**. Only the assistant's words are graded:
```
tokens:  \n User :  what 's  the capital ... \n Assistant :  Paris  . <eos>
labels:  -100 -100 -100 ... -100 ............ -100 -100 -100 Paris  . <eos>
```
A label of **`-100`** means "don't grade this position". Cross-entropy skips it, so its gradient is 0 (Chapter 15.1). The model learns *how to answer*, not how to imitate the user.

Same model, same backprop, same optimizer. Only the data and the grading mask change.

Every layer gets a pair of functions with the same pattern:

def layer_forward(x, params):
    ...                       # compute the output
    return out, cache         # cache = the notes the backward pass needs

def layer_backward(dout, cache):
    ...                       # apply the chain rule
    return dx, dparams        # dx goes to the previous layer; dparams are knob gradients
```

        logits, cache = gpt_forward(p, x, layers, heads)
        loss, ce = cross_entropy_forward(logits, y)
        grads = gpt_backward(cross_entropy_backward(ce), cache, p)
    for k, prm in params.items():
        prm.grad = grads[k]                                # hand them to the optimizer
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()
    print(step, loss.item())
```

Train a tiny model (width 64, 2 layers, context 64) on a slice of `val.bin` for a few hundred steps. Then run the *same* thing with `loss.backward()` and the same seed. **The two loss curves should overlap almost exactly.** When they do, your hand-written backprop is training a transformer.

(Your version will be slower and use more memory than the real one. PyTorch's `scaled_dot_product_attention` uses a clever fused algorithm that never stores the full `(t × t)` attention matrix. That's expected.)

## Appendix C: Answers to "Try it"

**Try it 2.1:** `y = [3, −1, 2]`.

**Try it 3.1:** With LR 0.3: step 1 → `w = 3 − 0.3·(−16) = 7.8`, guess 15.6 (overshot!). Step 2 gradient = `2·5.6·2 = 22.4` → `w = 7.8 − 6.72 = 1.08`, guess 2.16, even further off on the other side. It bounces back and forth and **diverges**. That's the "LR too big" picture from 3.5.

**Try it 4.1:** `"thats"` → `t h a t s` → (a+t) `t h at s` → (h+at) `t hat s` → (t+hat) **`that s`**. `"scat"` → `s c a t` → (a+t) `s c at` → (c+at) **`s cat`**.

**Try it 14.1:** Forward: `h = 1·2 = 2`, `y = 4·2 = 8`, `L = (8−5)² = 9`. Backward: `d_y = 2(8−5) = 6`. `d_w2 = 6·h = 12`. `d_h = 6·w2 = 24`. `d_w1 = 24·x = 48`. Check: `w1 = 1.001` → `h = 2.002`, `y = 8.008`, `L = 3.008² = 9.048064` → `(9.048064 − 9)/0.001 ≈ 48`. ✔

```python
"""Hand-written forward and backward passes for the GPT in model.py.

No autograd is used here: every gradient is computed by our own code.
Run `python manual_backprop.py` from the repo root to check every gradient
against PyTorch's autograd.
"""
import math
import torch

# ---------------------------------------------------------------- Linear
def linear_forward(x, W, b=None):
    y = x @ W.T
    if b is not None:
        y = y + b
    return y, (x, W, b is not None)


def linear_backward(dy, cache):
    x, W, has_bias = cache
    dx = dy @ W
    dy2 = dy.reshape(-1, dy.shape[-1])          # (positions, out)
    x2 = x.reshape(-1, x.shape[-1])             # (positions, in)
    dW = dy2.T @ x2                             # (out, in), summed over positions
    db = dy2.sum(0) if has_bias else None
    return dx, dW, db


# ---------------------------------------------------------------- GELU
def gelu_forward(x):
    return 0.5 * x * (1 + torch.erf(x / math.sqrt(2))), x


def gelu_backward(dy, x):
    cdf = 0.5 * (1 + torch.erf(x / math.sqrt(2)))
    pdf = torch.exp(-0.5 * x * x) / math.sqrt(2 * math.pi)
    return dy * (cdf + x * pdf)


# ---------------------------------------------------------------- LayerNorm
def layernorm_forward(x, gamma, beta, eps=1e-5):
    mu = x.mean(-1, keepdim=True)
    var = ((x - mu) ** 2).mean(-1, keepdim=True)
    rstd = 1 / torch.sqrt(var + eps)
    xhat = (x - mu) * rstd
    return xhat * gamma + beta, (xhat, rstd, gamma)


def layernorm_backward(dy, cache):
    xhat, rstd, gamma = cache
    c = xhat.shape[-1]
    dgamma = (dy * xhat).reshape(-1, c).sum(0)
    dbeta = dy.reshape(-1, c).sum(0)
    dxhat = dy * gamma
    dx = rstd * (dxhat
                 - dxhat.mean(-1, keepdim=True)
                 - xhat * (dxhat * xhat).mean(-1, keepdim=True))
    return dx, dgamma, dbeta


# ---------------------------------------------------------------- Softmax
def softmax_backward(dP, P):
    return P * (dP - (dP * P).sum(-1, keepdim=True))


# ---------------------------------------------------------------- Attention
def attention_forward(x, Wqkv, Wproj, heads):
    b, t, c = x.shape
    d = c // heads
    qkv, c_qkv = linear_forward(x, Wqkv)
    q, k, v = qkv.view(b, t, 3, heads, d).permute(2, 0, 3, 1, 4)   # each (b,h,t,d)
    S = q @ k.transpose(-2, -1) / math.sqrt(d)                      # (b,h,t,t)
    future = torch.triu(torch.ones(t, t, dtype=torch.bool), diagonal=1)
    P = S.masked_fill(future, float('-inf')).softmax(-1)
    Y = P @ v                                                        # (b,h,t,d)
    merged = Y.transpose(1, 2).reshape(b, t, c)
    out, c_proj = linear_forward(merged, Wproj)
    return out, (c_qkv, c_proj, q, k, v, P, heads)


def attention_backward(dout, cache):
    c_qkv, c_proj, q, k, v, P, heads = cache
    b, h, t, d = q.shape
    dmerged, dWproj, _ = linear_backward(dout, c_proj)
    dY = dmerged.view(b, t, h, d).transpose(1, 2)        # undo the merge
    dv = P.transpose(-2, -1) @ dY
    dP = dY @ v.transpose(-2, -1)
    dS = softmax_backward(dP, P)                          # masked spots: P=0 -> dS=0
    dq = dS @ k / math.sqrt(d)
    dk = dS.transpose(-2, -1) @ q / math.sqrt(d)
    dqkv = torch.stack([dq, dk, dv]).permute(1, 3, 0, 2, 4).reshape(b, t, 3 * h * d)
    dx, dWqkv, _ = linear_backward(dqkv, c_qkv)
    return dx, dWqkv, dWproj


# ---------------------------------------------------------------- Cross-entropy
def cross_entropy_forward(logits, targets):
    V = logits.shape[-1]
    flat, tgt = logits.reshape(-1, V), targets.reshape(-1)
    rows = (tgt != -100).nonzero().squeeze(1)       # positions that are graded
    logp = flat.log_softmax(-1)
    loss = -logp[rows, tgt[rows]].mean()
    return loss, (logp.exp(), tgt, rows, logits.shape)


def cross_entropy_backward(cache):
    P, tgt, rows, shape = cache
    d = torch.zeros_like(P)
    d[rows] = P[rows]
    d[rows, tgt[rows]] -= 1
    return (d / len(rows)).reshape(shape)


# ---------------------------------------------------------------- Whole GPT
def gpt_forward(p, ids, layers, heads):
    b, t = ids.shape
    x = p['tokens.weight'][ids] + p['positions.weight'][:t]
    caches = []
    for i in range(layers):
        n = f'blocks.{i}.'
        h1, c_ln1 = layernorm_forward(x, p[n + 'norm1.weight'], p[n + 'norm1.bias'])
        a, c_att = attention_forward(h1, p[n + 'qkv.weight'], p[n + 'proj.weight'], heads)
        x1 = x + a                                                    # residual 1
        h2, c_ln2 = layernorm_forward(x1, p[n + 'norm2.weight'], p[n + 'norm2.bias'])
        m1, c_fc = linear_forward(h2, p[n + 'mlp.0.weight'], p[n + 'mlp.0.bias'])
        g, c_gelu = gelu_forward(m1)
        m2, c_out = linear_forward(g, p[n + 'mlp.2.weight'], p[n + 'mlp.2.bias'])
        x = x1 + m2                                                   # residual 2
        caches.append((c_ln1, c_att, c_ln2, c_fc, c_gelu, c_out))
    xf, c_lnf = layernorm_forward(x, p['norm.weight'], p['norm.bias'])
    logits = xf @ p['tokens.weight'].T                                # tied head
    return logits, (ids, caches, c_lnf, xf)


def gpt_backward(dlogits, cache, p):
    ids, caches, c_lnf, xf = cache
    g = {name: torch.zeros_like(w) for name, w in p.items()}
    # tied head: logits = xf @ E.T
    dxf = dlogits @ p['tokens.weight']
    g['tokens.weight'] += dlogits.reshape(-1, dlogits.shape[-1]).T @ xf.reshape(-1, xf.shape[-1])
    dx, g['norm.weight'], g['norm.bias'] = layernorm_backward(dxf, c_lnf)
    for i in reversed(range(len(caches))):
        n = f'blocks.{i}.'
        c_ln1, c_att, c_ln2, c_fc, c_gelu, c_out = caches[i]
        # x = x1 + m2  -> blame flows to x1 directly AND through the MLP
        dg, g[n + 'mlp.2.weight'], g[n + 'mlp.2.bias'] = linear_backward(dx, c_out)
        dm1 = gelu_backward(dg, c_gelu)
        dh2, g[n + 'mlp.0.weight'], g[n + 'mlp.0.bias'] = linear_backward(dm1, c_fc)
        dx1_mlp, g[n + 'norm2.weight'], g[n + 'norm2.bias'] = layernorm_backward(dh2, c_ln2)
        dx1 = dx + dx1_mlp
        # x1 = x + a  -> same pattern
        dh1, g[n + 'qkv.weight'], g[n + 'proj.weight'] = attention_backward(dx1, c_att)
        dx_att, g[n + 'norm1.weight'], g[n + 'norm1.bias'] = layernorm_backward(dh1, c_ln1)
        dx = dx1 + dx_att
    # embeddings: scatter-add each position's blame into its token's row
    c = dx.shape[-1]
    g['tokens.weight'].index_add_(0, ids.reshape(-1), dx.reshape(-1, c))
    g['positions.weight'][:ids.shape[1]] += dx.sum(0)
    return g


# ---------------------------------------------------------------- Checks
def check(name, mine, ref, tol=1e-8):
    err = (mine - ref).abs().max().item()
    rel = err / (ref.abs().max().item() + 1e-12)
    ok = rel < tol
    print(f"{'OK ' if ok else 'BAD'} {name:28s} rel_err={rel:.1e}")
    return ok


if __name__ == '__main__':
    import sys
    from pathlib import Path
    sys.path.insert(0, str(Path(__file__).resolve().parent))
    sys.path.insert(0, str(Path.cwd()))
    from model import GPT
    from torch.nn import functional as F

    torch.set_default_dtype(torch.float64)
    torch.manual_seed(0)
    cfg = dict(vocab_size=50, context=16, width=16, layers=2, heads=2)
    model = GPT(**cfg)
    for prm in model.parameters():              # make every weight "interesting"
        prm.data.normal_(0, 0.3)
    ids = torch.randint(0, 50, (3, 10))
    targets = torch.randint(0, 50, (3, 10))
    targets[0, :4] = -100                       # like dialogue training

    logits = model(ids)
    ref_loss = F.cross_entropy(logits.reshape(-1, 50), targets.reshape(-1))
    ref_loss.backward()

    p = {k: v.detach() for k, v in model.state_dict().items()}
    my_logits, cache = gpt_forward(p, ids, cfg['layers'], cfg['heads'])
    my_loss, ce_cache = cross_entropy_forward(my_logits, targets)
    grads = gpt_backward(cross_entropy_backward(ce_cache), cache, p)

    ok = check('loss', my_loss, ref_loss.detach())
    for name, prm in model.named_parameters():
        ok &= check(name, grads[name], prm.grad)
    print('ALL GOOD' if ok else 'SOMETHING IS WRONG')
